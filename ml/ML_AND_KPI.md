# Насколько LUMEN зависит от яркости кадра

В этой проверке мы меняли яркость одного и того же изображения и считали, как часто модель сохраняет класс, заданный генератором. При исходной яркости модель верно распознала 400 из 400 сцен. При двукратном затемнении результат снизился до 256 из 400. В частности, на тёмном изображении модель часто перестаёт различать участки с неравномерным освещением.

| Яркость относительно исходной | Верный класс | Доля верных ответов |
|---|---:|---:|
| ×0,50 | 256 / 400 | 64,0% |
| ×0,75 | 394 / 400 | 98,5% |
| ×1,00 | 400 / 400 | 100,0% |
| ×1,25 | 400 / 400 | 100,0% |
| ×1,50 | 372 / 400 | 93,0% |

При ×0,50 модель приняла 66 из 80 сцен с неравномерным освещением за тёмные. При ×1,50 она приняла 21 из 80 сцен того же класса за освещённые. Если отбирать кандидатов на проверку по классу кадра, экспозиция камеры может менять и состав очереди. Связь такого изменения с реальными неисправностями нужно отдельно проверить в поле.

## Что именно проверили

Модель `3.0-demo-cv` получает изображение в градациях серого размером 48 × 48 пикселей. У неё два свёрточных слоя, два полносвязных слоя и 4 609 обучаемых параметров. Для обучения использовали 1 400 синтетических сцен. Файл `ml/metrics.json` содержит результат исходной проверки на 400 других синтетических сценах. Для настоящих городских камер качество ещё предстоит измерить.

Для нынешнего опыта генератор `scene()` создал 400 дополнительных сцен, по 80 каждого класса. Начальное значение генератора для каждого кадра задаёт формула `33000000 + 1000 * номер_класса + номер_сцены`, нумерация начинается с нуля. Для каждого кадра взяли пять множителей яркости, применили их ко всем пикселям, ограничили значения диапазоном [0, 1] и округлили до ближайшего 8-битного значения. Исходный класс во всех пяти случаях служил эталоном. Это проверка устойчивости к численному изменению яркости. Реальная камера также меняет шум, выдержку и обработку изображения.

Все 2 000 решений выдала функция приложения `cvInferPixels` из `vision.js` с поставляемыми весами `cv_model.js`. Пять результатов на один кадр связаны между собой. В файле `ml/exposure_results.json` записаны SHA-256 файла весов и пять матриц ошибок. Строки соответствуют исходным классам, столбцы — предсказанным. Классы по обеим осям идут в порядке `lit`, `dark`, `uneven`, `glare`, `day`.

### Воспроизведение

Из корня проекта выполните команду с Python 3, NumPy и Node.js 18 или новее. Повторное обучение не требуется.

```sh
python ml/exposure_benchmark.py
```

## Полевая проверка

До подключения камер команда может использовать приведённые ниже пороги как критерии пилота. Разметку событий делают проверяющие без подсказки модели. Камеры и даты итогового теста отделяют от данных для настройки. Последовательные кадры одного события объединяют до расчёта метрик, а выборку обычных интервалов просматривают вручную, чтобы обнаружить и пропущенные события.

| Вопрос пилота | С чем сравнивать и что считать | Цель |
|---|---|---|
| Находит ли модель проблемные участки? | Проверить CNN и простое правило по яркости и контрасту на одних и тех же размеченных событиях. Для каждой системы посчитать долю подтверждённых среди сигналов (precision) и долю найденных среди всех размеченных событий (recall). | Precision и recall ≥80% каждая |
| Сколько проверок окажутся напрасными? | Разделить число ложных событий на число полностью наблюдавшихся камера-ночей. Измерить обе системы при заранее зафиксированных порогах. | ≤1 ложного события на камеру за ночь |
| Ускоряет ли новая очередь работу? | На сопоставимых случаях сравнить обычную очередь по времени поступления и приоритетную очередь. Зафиксировать одинаковый бюджет проверок и измерить медиану времени от начала разбора до решения диспетчера. | Медианное время разбора ниже на 25% |

Чтобы проверить порядок заявок отдельно от скорости разбора, при одинаковом числе доступных выездов можно также сравнить число подтверждённых проблем среди первых K заявок в каждой очереди. Перенос на другие камеры и выводы об освещённости в люксах требуют самостоятельных измерений.
